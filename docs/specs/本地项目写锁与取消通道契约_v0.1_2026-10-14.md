## 1. 目标

同一项目的两个 Agent CLI 不能同时读取旧状态并覆盖对方的修改。除专门的取消通道外，每个修改命令必须在读取项目之前取得操作级独占锁，并持有到项目、台账、队列、操作记录和幂等记录的写入结束。不同项目可以独立执行。

`operations/project-write.lock` 是固定锁文件，Windows 用 `msvcrt.locking` 锁定首字节。文件持久保留，锁是否占用由操作系统决定；文件存在、PID 或时间戳都不是占用证据。进程退出或崩溃由操作系统释放锁，禁止通过删除锁文件来解锁。该文件不同于记录依赖版本的 `project.lock.json`。

## 2. 命令边界

时间线、素材导入/重链接/跟踪写回、项目快照/恢复/迁移、权利修改、模板、渲染和队列写入取得项目写锁。CLI 默认立即尝试，冲突返回 `PROJECT_WRITE_LOCKED`、退出码 6、`retryable=true`；竞争命令不得在取得锁之前创建快照、导入媒体、写操作或保存幂等响应。`queue cancel` 是第 3 节定义的唯一项目锁旁路。

项目检查、操作检查、权利查询、队列查询及 `--dry-run` 允许继续观察既有原子 JSON。它们读到的是已提交文件；本契约没有把多个 JSON 文件的原子替换提升为跨文件事务。Python 嵌入调用方需要显式使用 `project_write_lock` 包住完整读改写过程；直接编辑 JSON 的外部程序不受建议性锁约束。

## 3. 取消通道

队列运行持有项目写锁期间，`queue cancel` 必须仍可递交取消请求，不能排队等待渲染结束。取消标记通过同目录临时文件原子替换写入；取消命令不等待项目写锁，并在需要时尝试取得项目锁。

实现使用短生命周期的 `operations/queue-cancel.lock` 串行化取消标记、队列启动和终态提交的交界区；它只保护取消通道的几步状态转换，不会覆盖项目写锁，也不会在 FFmpeg 渲染期间持有：

- 项目锁空闲：读取最新队列，取消 pending 作业并保存状态，或为 running 作业写取消标记。
- 项目锁占用：只读取最新原子队列并写 `operations/queue-cancel/<job_id>.cancel`，不覆盖运行器持有的队列副本；响应声明 `acknowledged=true, confirmed=false`，表示取消请求已经递交，终态尚未确认。
- `queue list/inspect` 将标记映射为 `cancel_requested=true`，保持原有 pending/running 状态，直到运行器确认取消。
- 运行器在每个作业启动前和 FFmpeg 运行中检查标记；确认后保存 cancelled，保留审计记录并清理标记。
- 已成功或失败的作业拒绝取消；重复取消 cancelled 作业保持幂等。
- pending 作业上的新取消标记优先于启动请求；显式 `queue run --job-id ID` 对已 cancelled/failed 作业是重试授权，会清理上次尝试的标记并重新执行。清理后新到达的取消请求仍须有效。

取消响应不承诺已经生成的媒体被删除；最终结果以 `queue inspect` 的状态及 render 操作记录为准。

## 4. 恢复边界

正常退出、异常和进程终止均释放内核文件锁。锁文件保留供后续进程复用。当前防护覆盖合作 CLI 之间的读改写互斥；跨文件事务回滚、断电时项目/台账组合恢复、孤立 running 作业的恢复和多机调度仍需独立契约和故障样例，不能凭锁测试声明已实现。

## 5. 验收

验收必须使用两个真实本地 Python 进程：竞争写入拒绝且项目字节不变、只读与 dry-run 仍可用、释放后修改成功、持锁进程被终止后可重新修改。队列测试必须证明持锁时取消标记成功递交且不会覆盖队列、运行器确认取消、显式重试可执行。所有样例在 E 盘运行时目录内完成。
