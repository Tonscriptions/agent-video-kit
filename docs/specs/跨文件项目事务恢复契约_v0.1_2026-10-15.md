| 版本 | 0.1.0 |

| 适用范围 | Agent CLI 对既有本地项目的协作式写入 |
| 运行策略 | 原生 Windows、Python、FFmpeg；无 Docker、WSL、守护进程、网络服务 |

## 1. 目的与边界

项目写锁只能防止两个合作进程同时读改写，不能防止进程在 `project.json` 已替换、Rights Ledger 尚未替换时断电。本契约在写锁内增加一个短生命周期、可检查的本地事务日志，使下一次 CLI 启动或显式 `project recover` 可以恢复项目元数据的一致版本。

事务覆盖以下小型元数据文件：

- 根目录的 `project.json`、`rights-ledger.json`、`project.lock.json`；
- `operations/`、`history/`、`validation/`、`exports/` 下的记录文件；
- 固定锁文件、事务日志和事务备份目录本身不纳入备份清单。

`assets/`、`renders/`、`cache/` 中的媒体、代理、缓存和 FFmpeg 中间产物不复制到事务备份。恢复会保留这些文件并在结果中声明 `side_effect_scope`，交给 Agent 依据哈希和操作记录复核，避免为了元数据回滚复制整套媒体。

## 2. 日志格式和状态机

事务日志固定为 `operations/project-transaction.json`，版本为 `0.1.0`。准备阶段写入：

```json
{
  "transaction_version": "0.1.0",
  "transaction_id": "txn_...",
  "status": "prepared",
  "command": "timeline.compose",
  "scope": "project-metadata-v1",
  "started_at": "2026-10-15T00:00:00Z",
  "files": [
    {
      "path": "project.json",
      "backup": "operations/project-transaction-backups/txn_.../0000.bin",
      "size": 1234,
      "sha256": "..."
    }
  ]
}
```

状态只有：

| 状态 | 含义 | 下一个动作 |
|---|---|---|
| `prepared` | 备份已经 fsync，写入尚未确认完成 | 恢复清单中的原始字节，删除事务期间新增的元数据记录 |
| `committed` | 所有命令写入已完成，提交标记已 fsync | 只清理日志和备份，不回滚文件 |
| 日志不存在 | 没有待处理事务 | 返回 `clean` |

每个备份文件都写在项目内同一操作目录，日志通过原子 JSON 替换写入。提交顺序是先写 `committed`，再删除备份和日志；因此在清理过程中再次中断也只会执行幂等清理。

## 3. CLI 语义

`project recover --project PATH` 在项目写锁内读取事务日志：

- `prepared`：恢复原始元数据，删除本次事务新建的 `operations/history/validation/exports` 记录，返回 `status=recovered`、恢复列表、删除列表和媒体副作用范围；
- `committed`：清理遗留备份，返回 `status=committed_cleaned`；
- 无日志：返回 `status=clean`；
- `--dry-run` 只报告是否存在日志，不创建备份、操作记录或恢复文件。

除 `project recover` 外，合作式项目写命令在取得 `operations/project-write.lock` 后会先执行同样的预恢复检查。发现上次 `prepared` 日志时，恢复完成后继续本次命令，并在 envelope `warnings` 加入 `PROJECT_TRANSACTION_RECOVERED`。

命令执行顺序为：

1. 取得项目写锁；
2. 恢复遗留 `prepared` 日志；
3. 备份事务范围并写入 `prepared` 日志；
4. 执行项目、Rights Ledger、队列和操作记录的读改写；
5. 所有写入成功后写入 `committed` 并清理；
6. 异常退出时由当前进程立即恢复，强制终止/断电则留给下一次预恢复或 `project recover`。

## 4. 错误和安全规则

- 事务日志、备份路径必须解析到当前项目目录内；越界、未知状态、缺失备份或非法文件项返回 `PROJECT_TRANSACTION_*`，退出码 6，并拒绝猜测恢复。
- 恢复只接受日志列出的相对路径；不会跟随项目外符号链接写入。
- 固定 Windows 锁文件不能被恢复逻辑删除或覆盖；锁释放依旧由操作系统负责。
- 事务不绕过 Rights Ledger、schema、路径 allowlist、网络禁用和发布门禁。命令已经明确写入的 `failed`、`cancelled` 或 `partial` 操作记录属于审计事实；当前进程异常回滚时会在恢复项目元数据后保留这些记录，以便 `render --resume`、`queue inspect` 和 Agent 诊断继续工作。
- 外部 JSON 编辑器不自动参加写锁或事务。直接修改项目后仍应运行 `validate`、`policy audit` 和显式 `project snapshot`；外部程序不应在合作 CLI 持锁时写入。

## 5. 验收证据

最小回归必须覆盖：

1. 人工留下 `prepared` 日志后修改 `project.json`、`rights-ledger.json` 并增加操作记录，`project recover` 恢复原始字节并删除新增记录；
2. 无日志的 `project recover` 返回 `clean`，`--dry-run` 不改变目录清单；
3. 快照、迁移和时间线写入在正常完成后不会留下事务日志或备份目录；
4. 恢复后的项目仍通过 schema/语义校验，写锁竞争和队列取消语义保持不变。

对应测试：`test_project_transaction_recovery_restores_metadata_and_removes_new_records`、`test_project_recover_cli_reports_noop_and_dry_run_without_writing`、`test_project_snapshots_restore_edit_state`、`test_project_migrate_legacy_defaults_and_backup`。

## 2026-10-15 模型登记侧车增量

`models/audio-adapters.json` 与 `models/visual-adapters.json` 纳入小型元数据事务与快照，首次登记失败会删除新建侧车，既有侧车失败会按原字节恢复。快照使用固定相对路径 `model_registries`，恢复可恢复已登记列表或移除快照时不存在的侧车；不扫描/复制大型权重。旧快照不含该字段时保留当前侧车，不推断历史模型状态。

## 2026-10-16 失败诊断保留

正常异常回滚时，除既有失败操作记录外，还保留该 `AppError.path` 明确指向的项目 `validation/` 内 JSON：顶层须有 `report_version` 且 `status` 为 `failed/cancelled/partial`。先恢复项目/台账/事务元数据，再按实际字节保留该诊断；不会扫描保留其他失败核验文件。成功或无版本报告仍回滚到原始字节。错误路径非法时不覆盖原异常。

此规则用于蒙版检查失败的可复核证据；不改变强制终止/断电后的恢复规则，后者没有当前异常可用于选择诊断。真实失败门禁、项目未改动、无关失败文件不保留与原始错误不被遮蔽，见[蒙版锚定实测](../validation/本地蒙版驱动锚定与重构图实测_2026-10-16.md)。
