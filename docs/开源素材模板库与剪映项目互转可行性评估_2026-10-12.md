# 开源素材/模板库与剪映项目互转：可行性评估


| 文档编号 | RESEARCH-2026-10-003 |
|---|---|
| 状态 | 有效 |
| 本次审计复核 | 2026-10-13 |
| 证据性质 | 可行性研究；转换器尚未实现 |
更新时间：2026-10-12  
目标：在无剪映运行时依赖的开源 Agent 视频软件中，建设可验证授权的素材库和模板库，并提供剪映项目的导入/导出兼容层。

## 1. 结论先行

| 目标 | 可行性 | 结论 |
|---|---|---|
| 建设开源素材库 | **可行** | 可以聚合 CC0、Public Domain、CC BY 等开放许可资源，但必须保存来源、作者、许可证、原始 URL、下载时间、哈希和授权证据。 |
| 建设开源模板库 | **可行** | 模板本身可以用 Apache-2.0、MIT、CC0、CC BY 或项目自定义开放协议发布；模板内嵌素材仍要逐项继承许可证。 |
| 剪映项目导入到新软件 | **部分可行** | 简单轨道、媒体、文本、速度、音量、基础关键帧和部分效果可以映射；复杂效果、复合片段、加密草稿和在线资源不能保证。 |
| 新软件项目导出为剪映项目 | **有限可行** | 可以针对特定剪映/CapCut 版本生成部分草稿结构，但属于版本适配，不是稳定公开标准。 |
| 剪映与新软件双向无损互转 | **不可作为总体承诺** | 私有草稿格式、加密/混淆字段、资源 ID、字体、特效参数和 AI 结果无法保证双向保真。 |
| 直接把剪映素材变成“开源素材” | **不可行** | 格式转换不会改变著作权和授权；只能在用户拥有授权、或原资源本来就是开放许可时进入开源素材库。 |

最合理的产品承诺是：

**开放许可素材与模板库 + 可解释的剪映项目导入器 + 有限版本的剪映草稿导出器 + 永远以自有开放项目格式为主格式。**

## 2. 必须区分的三个概念

### 2.1 软件开源

软件源代码使用 AGPL、Apache、MIT 等许可证发布。

### 2.2 素材开放许可

素材仍然有著作权，只是著作权人提前授予部分使用权。Creative Commons 明确区分 CC BY、CC BY-SA、CC BY-NC、CC BY-ND 等不同条件；CC BY 允许商业使用但要求署名，CC BY-SA 还要求衍生作品采用相同或兼容条款，CC BY-ND 不允许衍生，CC BY-NC 不允许商业使用。[Creative Commons 许可证说明](https://creativecommons.org/cc-licenses/)

### 2.3 内容转换

把剪映草稿转换为 JSON、OTIO、MLT 或本软件项目文件，只改变表达方式，不改变视频、音乐、字体、人物肖像、商标和模板资产的权利归属。

## 3. 开源素材库的正确定位

不要把库命名为“全部免费素材库”，应定位为：

**带授权证据的开放许可媒体注册表和本地镜像。**

可接入的来源类型：

| 来源 | 适合作用 | 注意点 |
|---|---|---|
| Openverse | 搜索开放许可图片和音频的入口 | 结果是发现层，下载前仍要保存原始来源和许可证证据 |
| Wikimedia Commons | 图片、视频、音频和公共领域内容 | 每个文件页面的许可、作者和来源都要单独核验；Wikimedia 也提醒上传者不一定是原作者 |
| Freesound | 搜索和获取音效及音频元数据 | API 可查询音频、用户、包和分析特征，但每个声音的许可证和署名条件仍需入库 |
| NASA、政府开放数据、公共机构 | 公共领域或政府许可的素材 | 需要核对具体机构、国家和数据集条款 |
| 用户上传 | 建立自己的素材贡献网络 | 必须要求权利声明、许可证选择、来源、肖像/场地/商标授权和撤下机制 |

Openverse 的定位是开放许可和公共领域媒体的搜索入口；Freesound 提供音频及其元数据 API。[Openverse 项目](https://github.com/WordPress/openverse)、[Freesound API 文档](https://freesound.org/docs/api/)

### 3.1 推荐的素材记录

每个素材必须有一条不可变的 rights record：

| 字段 | 用途 |
|---|---|
| asset_id | 内部稳定 ID，不使用来源网站的短 ID 作为唯一标识 |
| file_sha256 | 文件完整性和去重 |
| media_type | video、image、audio、font、sticker、template |
| source_url | 原始页面，不只保存下载地址 |
| source_platform | Openverse、Commons、Freesound、用户投稿等 |
| title、creator | 署名和搜索 |
| license_spdx / license_url | 机器判断许可证 |
| attribution_text | 自动生成片尾、描述或交付清单 |
| commercial_use | 是否允许商业广告 |
| derivative_use | 是否允许剪辑、裁切、混音、变速和 AI 处理 |
| share_alike | 是否触发同许可传播 |
| model_release | 人物肖像、声音、表演是否有授权 |
| property_release | 场地、建筑、商标、产品外观是否有授权 |
| territory、expires_at | 地域和期限限制 |
| evidence_url、evidence_snapshot | 授权证据和抓取时间 |
| downloaded_at、mirror_status | 本地镜像状态 |
| takedown_status | 撤下、争议和冻结状态 |

Creative Commons 推荐将 Title、Author、Source、License，也就是 TASL，一起保留；只在视频文件里写一个“CC”不能满足可靠追溯。[CC 署名最佳实践](https://wiki.creativecommons.org/wiki/Best_practices_for_attribution)

### 3.2 广告场景的许可证分层

建议把素材分成四层：

| 层 | 允许进入默认广告模板吗 | 典型许可 |
|---|---:|---|
| A | 可以 | CC0、Public Domain、明确允许商业使用且允许改编的 CC BY |
| B | 可以，但交付必须自动附署名 | CC BY、部分 CC BY-SA |
| C | 只允许非商业或内部演示 | CC BY-NC、带限制的教育许可 |
| D | 不进入默认广告库 | CC BY-ND、授权不清、人物/商标/场地权利缺失、来源争议 |

音乐还要区分录音版权、词曲版权、表演者权利和平台使用条款。所谓 royalty-free 不等同于开放许可。

## 4. 开源模板库的设计

模板不是一个视频文件，而是：

**项目结构 + 资产依赖 + 参数约束 + 授权清单 + 预览 + 能力要求。**

推荐模板包：

| 文件/目录 | 内容 |
|---|---|
| template.json | 模板 schema、版本、画幅、帧率、时长范围、可替换槽位 |
| project.json | 本软件的可编辑项目 |
| project.otio | 基础时间线交换文件 |
| media/ | 允许重新分发的本地素材或指向外部素材的哈希引用 |
| fonts/ | 有再分发权的字体，或只写字体名称和回退策略 |
| previews/ | 封面、低清预览、关键帧和示例成片 |
| licenses/ | 每个资产的许可证、署名和证据快照 |
| checksums.json | 文件哈希和包完整性 |
| capabilities.json | 所需渲染后端、模型、效果包和最低版本 |
| warnings.json | 不支持的效果、降级规则和已知差异 |

模板替换必须使用槽位：

- video_slot：画面比例、主体安全区、最短/最长时长；
- image_slot：裁切模式、焦点位置、遮罩；
- voice_slot：语言、音色、响度、字幕策略；
- text_slot：字数、字体、描边、最大行数；
- music_slot：BPM、时长、音乐许可；
- logo_slot：透明度、最小尺寸、品牌安全区。

模板不能把剪映的 resource_id 当作唯一依赖。应使用本软件 asset_id，并允许导入器把剪映资源转换成 external reference 或 replacement slot。

## 5. 剪映项目转换的现实边界

### 5.1 已有开源工具说明了什么

现有开源项目证明“读取和生成部分剪映草稿”是可行的，但同时证明了兼容性不是稳定标准：

- pyJianYingDraft 支持部分剪映草稿生成、模板替换、文本替换和轨道导入；其 README 明确写到新版 draft_content.json 可能不是可直接读取的明文 JSON，需要额外读取器，模板导入也有操作限制。[pyJianYingDraft](https://github.com/GuanYixuan/pyJianYingDraft)
- pyCapCut 支持未加密 draft_content.json 的模板模式、素材替换、文本替换、轨道导入和部分关键帧/遮罩/效果，但 README 把模板、批量导出、动画/效果/转场模块标为迁移中或需要进一步验证。[pyCapCut](https://github.com/GuanYixuan/pyCapCut)
- capcut-draft 的公开案例明确说明：项目交接可以保留画面、配音、图片和文字时间安排，但特殊字体、逐词颜色动画、部分裁切和阴影会有差异；它不承诺任意版本、任意效果组合或双向无损转换。[capcut-draft](https://github.com/ss-cmd/capcut-draft)

因此，转换器应当是“版本化、可降级、出具警告”的适配层，而不是声称一键无损。

### 5.2 支持等级

| 支持级别 | 内容 | 处理策略 |
|---|---|---|
| Exact | 媒体引用、片段起止、轨道顺序、帧率、基础变换、音量、普通文本 | 直接映射并保留原始字段 |
| Mapped | 关键帧、淡入淡出、基础转场、字幕样式、常见滤镜 | 映射到本软件参数，并记录源字段 |
| Approximate | 复杂特效、花字、遮罩、复合片段、动画曲线、音频特效 | 选择近似效果，写入差异和预览 |
| Baked | 无法结构化表达但可以渲染的画面 | 以中间视频/透明序列固化，保留原片段元数据 |
| Unsupported | 加密字段、在线模板、云资源、缺失媒体、未知模型结果 | 停止或生成明确错误，不静默丢失 |

### 5.3 不应做的事情

- 不绕过账号、付费、加密或 DRM；
- 不打包或重新分发剪映私有模型、特效资源、字体和在线模板；
- 不把剪映草稿里的第三方素材自动标成开源；
- 不在转换失败时静默删除效果；
- 不以一个成功打开的草稿宣称全部功能兼容。

## 6. 推荐的双向交换模式

### 6.1 本软件的规范主格式

采用“自有规范 JSON + OTIO + 可选 MLT”的三层结构：

| 格式 | 角色 |
|---|---|
| Agent Project JSON | 主格式，表达关键帧、遮罩、效果参数、字幕、素材权利和 Agent 任务信息 |
| OTIO | 基础剪辑交换格式，表达时间线、剪辑顺序和外部媒体引用 |
| MLT XML | 需要与 MLT/Kdenlive 生态交换时使用 |
| EDL/AAF/FCP XML | 面向传统 NLE 的有限兼容出口，不作为主格式 |

OpenTimelineIO 是开源的编辑时间线交换 API/格式，包含剪辑顺序和外部媒体引用，但不是媒体容器；它支持通过 adapter 读写 FCP XML、AAF、CMX 3600 EDL 等格式。[OpenTimelineIO](https://github.com/AcademySoftwareFoundation/OpenTimelineIO)

MLT 提供 producer、playlist、multitrack、filter、transition 和 XML 序列化能力，适合作为另一条开源渲染/交换路线，但其效果语义仍不能承载剪映全部私有参数。[MLT Framework](https://github.com/mltframework/mlt)、[MLT Framework 文档](https://www.mltframework.org/docs/framework/)

### 6.2 剪映导入流程

1. 由用户选择自己有权访问的剪映草稿目录或导出的交换文件。
2. 读取可公开解析的草稿字段和媒体引用。
3. 将本地媒体复制或链接到导入包，计算哈希。
4. 把轨道、片段、时间码、基础变换、音量、字幕和关键帧映射到 Agent Project JSON。
5. 对每个效果给出 Exact、Mapped、Approximate、Baked 或 Unsupported 状态。
6. 生成导入报告、缺失资源清单、许可证清单和预览 contact sheet。
7. 通过本软件渲染，完成视觉、音频和时码验收。

### 6.3 本软件导出为剪映草稿

1. 只针对已验证的剪映/CapCut 版本建立 adapter profile。
2. 先生成受支持的基础草稿结构。
3. 对不支持的效果采取用户选择的近似、固化或拒绝策略。
4. 生成 draft package 和单独的 conversion report。
5. 由用户在本地剪映中打开并验收；不能把本地登记成功视为画面保真。

### 6.4 剪映与本软件之间的开放包

推荐输出：

| 文件 | 作用 |
|---|---|
| project.json | 本软件完整可编辑项目 |
| project.otio | 标准时间线交换 |
| media/ | 用户有权打包的媒体 |
| source-links.json | 未复制媒体的原始路径、哈希和来源 |
| rights/ | 每个素材的许可证和署名 |
| conversion-report.json | 精确映射、近似映射、固化和丢弃项目 |
| preview/ | 导入前后关键帧和低清成片 |
| manifest.json | 软件版本、适配器版本、模型、字体和效果包 |

## 8. 建议的软件模块

| 模块 | 责任 |
|---|---|
| open-media-registry | 索引、搜索、来源、许可证、署名和哈希 |
| rights-ledger | 授权证据、肖像/场地/商标授权、撤下和争议 |
| asset-mirror | 下载、断点、哈希校验、病毒/格式检测和本地缓存 |
| template-registry | 模板版本、槽位、预览、能力和许可证依赖 |
| canonical-project | Agent Project JSON、OTIO、MLT 和版本迁移 |
| jianying-adapter | 只处理已授权的剪映草稿和标准交换文件 |
| capcut-adapter | 针对国际 CapCut 的独立版本适配，不与 Jianying 假设完全共用 |
| render-runtime | Concat headless runtime、FFmpeg、GPU/CPU 后端 |
| ai-workers | ASR、VAD、跟踪、抠像、补帧、音频分离、TTS |
| conversion-qa | 时码、像素、响度、帧数、字幕溢出、色彩和许可证检查 |
| agent-interface | CLI、JSON-RPC、gRPC、MCP，共用相同 request/result schema |

## 9. 工程量估算

不包含训练基础模型、购买版权库和建设大规模 CDN。

| 阶段 | 交付 | 粗略工程量 |
|---|---|---:|
| M0 | 开放许可资产 schema、rights ledger、下载与哈希 | 2–4 人月 |
| M1 | 本地素材仓、搜索、许可证过滤、署名清单 | 4–8 人月 |
| M2 | 模板 schema、槽位替换、预览和版本管理 | 4–8 人月 |
| M3 | Agent Project JSON、OTIO/MLT 双向基础适配 | 4–9 人月 |
| M4 | 剪映导入器：媒体、轨道、文本、速度、音量、基础关键帧 | 4–10 人月 |
| M5 | 剪映导出器：固定版本、有限效果、转换报告 | 6–12 人月 |
| M6 | 复杂效果、复合片段、字幕动画、色彩和音频适配 | 9–18 人月 |
| M7 | 版权运营、撤下、争议处理、审核、镜像和持续兼容 | 持续投入 |

如果目标只是让 Agent 使用开放素材制作广告，先做 M0–M3；如果目标是“任意剪映工程双向无损转换”，项目风险会从工程问题升级为私有格式、版本、资源和法律边界问题。

## 10. 最终建议

### 建议做

1. 建立自有开放项目格式，主格式采用 Agent Project JSON，OTIO 作为基础时间线交换。
2. 建立 rights ledger，把素材下载、授权和署名当成一等数据。
3. 先做 CC0/Public Domain/明确商业可改编的 CC BY 素材集合。
4. 模板中只引用有明确再分发权的资产；受限资产只作为外部引用，不打包进发行版。
5. 剪映转换采用 loss-aware adapter，所有降级都生成报告。
6. 用成片 MP4 作为最终兜底，用可编辑工程作为尽力而为的交付。

### 不建议做

1. 宣称支持“任意剪映版本、任意模板、任意特效的无损双向转换”。
2. 把剪映草稿里的素材自动纳入开源库。
3. 把未经授权的在线模板、贴纸、音乐、字体和模型资源镜像到发行版。
4. 把私有草稿解密、绕过账号或付费能力作为产品方案。
5. 以“能在剪映里打开”代替视觉、音频、时码和许可证验收。

## 11. 最终判断

这个方向**可行**，但产品应分成两个边界：

- **可交付边界：** 开放许可素材/模板库 + Agent-first 视频内核 + 剪映项目的有限、可解释导入/导出。
- **不可承诺边界：** 任意版本剪映工程的双向无损转换，以及把剪映内的第三方内容自动变成开源内容。

最稳妥的路线是先建设“开放资产和自有模板生态”，再把剪映兼容层作为输入输出适配器，而不是让剪映私有格式成为整个软件的内部主格式。
