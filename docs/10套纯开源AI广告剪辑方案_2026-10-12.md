# 10 套纯开源 AI 广告剪辑方案


| 文档编号 | PLAN-2026-10-001 |
|---|---|
| 状态 | 草案 |

设计日期：2026-10-12，Asia/Taipei。目标是让 Agent 制作达到剪映同类广告成片水准的视频，重点包括素材混剪、AI 特效、关键帧和运镜预设。

**建议以方案 1 建立生产主线，接入方案 4 的内容流水线，再按需求加入方案 7、8 的包装能力，最终演进到方案 10。** 方案 5 的 Concat 保留为内核研发路线。

这 10 套是不同的生产架构，不是已经安装并验收的整包。现有源码与上游测试能证明部分能力存在；尚未在本机制作对照样片，因此不能声称其中任一套已经全面达到剪映的产品功能、模板规模和自动化体验。

所有方案使用原生 Windows 程序及开源制作组件；不调用剪映，不采用 Docker、WSL 或其他虚拟化环境。AI 部分选用许可证已核查的推理代码和模型权重，仍需做 Windows 集成与输出质量验收。本文所有新 Skill 名称均为**建议注册名**，本轮没有安装或注册这些新 Skills。

## 10 套方案总览

下表按生产定位编号，不按 Star 或未经实测的质量分数排序。建设量是相对判断，依据需要新增的适配器、模板和验证范围，不代表工期承诺。

| 2 | 可人工复修的专业剪辑 | Kdenlive + dcc-mcp-kdenlive | `$video-cut-kdenlive-workflow` | 多轨、字幕、调色、较复杂广告 | 中 |
| 3 | 批量广告与版本管理 | Kdenlive + AMMIROSOH/Kdenlive-mcp | `$video-cut-kdenlive-batch` | 多商品、多文案、多比例的广告变体 | 中至高 |
| 4 | 中文解说与叙事混剪 | FFmpeg + video-recap-skills + 本地开源 AI | `$video-cut-recap` | 口播、测评、解说型带货、长素材精剪 | 中 |
| 5 | Agent 原生内核研发 | Concat + run-concat + Recap 流程适配 | `$video-cut-concat-editor` | 自研编辑系统、自然语言编辑实验 | 高 |

## 方案 1：Shotcut 通用广告工作台

- **程序与入口：** Shotcut 保存 `.mlt` 工程；`matrodrigs/shotcut-mcp` 提供结构化编辑、关键帧和渲染入口；FFmpeg 负责素材标准化和交付检查。拟建 `$video-cut-shotcut-pipeline`，复用已安装的 `$video-cut-ad-creative` 和 `$video-cut-ffmpeg`。
- **制作流程：** 广告简报 → 选段与镜头表 → 多轨时间线 → 命名运镜预设 → 字幕、声音、品牌包装 → 预览检查 → 渲染。需要转写时加入 Whisper。
- **关键帧与运镜：** 已核实 `animate_clip` 的片内帧坐标、中心位置、缩放、旋转、透明度、音量和插值接口，以及速度映射。可在此封装推近、拉远、横移、Ken Burns、节拍缩放等配方；单次动画接口最多 64 个关键帧点。
- **需要补齐：** 标准 `SKILL.md`、广告模板、命名预设、节拍适配、中文字体与字幕流程。MCP 操作保存的工程，不掌握 GUI 未保存的修改；不能把所有 Shotcut GUI 功能都计为已接通的 Agent 能力。
- **质量目标与交付：** 优先验证常见 15–30 秒电商和实拍混剪广告，交付 MP4、字幕、`.mlt` 工程和素材清单。上游有 Windows 的真实 MLT 渲染测试，本机仍待验收。**这是当前最建议先做的方案。**

依据：[Shotcut](https://shotcut.org/features/)、[MCP 源码与文档](https://github.com/matrodrigs/shotcut-mcp)、[结构化动画接口](https://github.com/matrodrigs/shotcut-mcp/blob/f1b78d350a9992296f0b7f11a55c04819ea25730/shotcut_mcp/tools.py)、[Windows 渲染 CI](https://github.com/matrodrigs/shotcut-mcp/blob/f1b78d350a9992296f0b7f11a55c04819ea25730/.github/workflows/shotcut-integration.yml)。

## 方案 2：Kdenlive 专业剪辑与人工复修

- **程序与入口：** Kdenlive + `dcc-mcp/dcc-mcp-kdenlive`。该仓库实际存在 9 个标准 Skills，其中 8 个常规包、1 个实验性 native 包。拟建 `$video-cut-kdenlive-workflow`，按需将常规包改名为 `$video-cut-kdenlive-project`、`$video-cut-kdenlive-media`、`$video-cut-kdenlive-timeline`、`$video-cut-kdenlive-effects`、`$video-cut-kdenlive-catalog`、`$video-cut-kdenlive-export`、`$video-cut-kdenlive-interchange`、`$video-cut-kdenlive-setup`。
- **制作流程：** Agent 建立工程、素材与粗剪 → 配置特效和字幕 → 原生 Kdenlive 打开复修 → 保存后继续 Agent 渲染和检查。强调可读、可改的工程交付。
- **关键帧与运镜：** 将推拉、平移、旋转等预设编译为原生特效的参数与关键帧字符串；每个配方需要核对滤镜版本、属性名与坐标含义。
- **需要补齐：** 相机预设库、共享素材 producer 的隔离策略、中文成片检查和 Windows 真实渲染。跟踪等部分操作走 GUI 路线；常规文件编辑不需要实验性实时桥接。实时 native 包依赖定制构建，不能当作官方安装包已有功能。
- **质量目标与交付：** 面向多轨和需要人工精修的广告，交付 `.kdenlive` 工程、素材清单、MP4 与字幕。比方案 1 更强调现成 Skill 和人工复修；适配器的本机 Windows 全流程证据仍需补充。

依据：[DCC 适配器](https://github.com/dcc-mcp/dcc-mcp-kdenlive)、[实际 Skill 目录](https://github.com/dcc-mcp/dcc-mcp-kdenlive/tree/5a83cbad7c987e32b86a5314996951ac91311c3b/src/dcc_mcp_kdenlive/skills)、[Kdenlive 关键帧文档](https://docs.kdenlive.org/en/effects_and_filters.html)。

## 方案 3：Kdenlive 批量广告与版本管理

- **程序与入口：** Kdenlive + `AMMIROSOH/Kdenlive-mcp`，使用版本化 JSON 作为源工程，编译 MLT 并导出可编辑 Kdenlive 工程。拟建 `$video-cut-kdenlive-batch`；上游有 MCP 和编辑配方，本次未找到标准 `SKILL.md`。
- **制作流程：** 统一模板与商品变量表 → 生成每个变体的独立 JSON → 修订检查 → 预览 → 排队渲染 → 质量检查 → 按商品、文案和比例归档。先用少量变体验证，再扩大批次。
- **关键帧与运镜：** 模板保存镜头时长和关键帧配方，替换商品、字幕与画幅时重新计算运动参数。变体之间保留独立修订和回滚点。
- **需要补齐：** 批量驱动 Skill、模板参数校验、画幅重排、失败重试和品牌一致性检查。上游的本地 AI 分析仍属于规划项；有 JSON、队列和关键帧不代表已实现自动广告创作。
- **质量目标与交付：** 面向同一产品多个 Hook、CTA 和画幅的批量广告，交付 JSON、`.kdenlive` 工程、预览与 MP4。上游将 Windows 10/11 x64 标为 Tested，列出 Kdenlive 26.04.2/MLT 7.39.0；这是上游声明，尚非本机验证。

依据：[程序与修订/队列能力](https://github.com/AMMIROSOH/Kdenlive-mcp)、[运行环境声明](https://github.com/AMMIROSOH/Kdenlive-mcp/blob/b1ff6d5d0263c9074230b9a5d02a6a5d58d2386e/docs/runtime-support.md)。

## 方案 4：video-recap 中文解说与叙事混剪

- **程序与入口：** FFmpeg + `zenstory-ai/video-recap-skills`。7 个上游 Skills 建议映射为 `$video-cut-recap`、`$video-cut-recap-understanding`、`$video-cut-recap-script`、`$video-cut-recap-cut`、`$video-cut-recap-voiceover`、`$video-cut-recap-assemble`、`$video-cut-recap-reference`。
- **制作流程：** 长素材 → 画面/语音理解 → 广告叙事与选段 → 切片 → 配音 → 字幕、混音、包装 → FFmpeg MP4 与 QC。优先复用它已有的切片、音频、字幕和时间线契约。
- **开源 AI 改造：** ASR 接 Whisper；TTS 接 Kokoro-82M 或使用已有录音；画面理解可选 Apache-2.0 的 Qwen2.5-VL-7B-Instruct。接入须适配输出格式、时间戳和模型服务，不能只替换 API 地址。
- **关键帧与运镜：** 原有声音关键帧与对白保护机制有用，但画面包装主要为静态层。推拉、卡点和花字运动要另加 FFmpeg 配方，或通过新增适配器送到方案 1。
- **需要补齐：** 默认 MiMo/Fish 服务的替换、字幕对齐、Windows 模型运行和画面运动。上游已有 `index-tts` 自托管 JSON→WAV 入口，但传输接口不能证明后面的具体模型符合本项目的开源要求。剪映导出保持关闭，不采用可选 Remotion 包装流程。
- **质量目标与交付：** 最适合先做中文解说、测评和带货广告，交付 MP4、字幕、脚本、选段清单和中性 `timeline.json`。原有时间线并不自动等于 Shotcut/Kdenlive 可编辑工程，需要转换。

依据：[Recap 仓库](https://github.com/zenstory-ai/video-recap-skills)、[真实 FFmpeg 合成代码](https://github.com/zenstory-ai/video-recap-skills/blob/539168622918e058bd250c793b82f043eced31e0/skills/video-assemble/scripts/assemble.py)、[默认关闭剪映导出](https://github.com/zenstory-ai/video-recap-skills/blob/539168622918e058bd250c793b82f043eced31e0/skills/video-assemble/scripts/lib.py)。模型依据见后文。

## 方案 5：Concat Agent 原生内核研发

- **程序与入口：** 独立开源编辑器 Concat + 官方 `run-concat`；建议将官方 Skill 命名为 `$video-cut-run-concat`，另建创作入口 `$video-cut-concat-editor`。`run-concat` 负责开发构建、启动与修改验证。
- **制作流程：** 素材与广告脚本 → 借鉴/改造 Recap 生成选段和音频计划 → 新增 Concat 时间线适配 → CLI/JSON-RPC 等已核实接口 → 预览与导出 → 原生工程交付。
- **关键帧与运镜：** 围绕 Concat 的关键帧能力建立镜头配方；必须逐项实测 UI 状态、实际渲染和导出结果一致，不能把 README 声明的全部自动化接口都视为已经验收。
- **需要补齐：** 广告创作 Skill、Recap 转换器、字幕/包装、运镜模板以及 Windows 发布和导出验证。当前没有核实到 Recap 与 Concat 已有官方适配器。
- **质量目标与交付：** 适合自研 Agent 编辑系统和接口演进，暂不作为第一条交付主线。补查时最新 v0.2.6 的 Windows 发布包问题 #303 仍开放；这影响该版本优先级，不代表所有未来构建都不能运行。

依据：[Concat](https://github.com/jub0t/concat)、[官方 run-concat Skill](https://github.com/jub0t/concat/blob/fa51932e73d30bc01a9acd3e2910d7602bba9ca0/.claude/skills/run-concat/SKILL.md)、[Windows 问题 #303](https://github.com/jub0t/concat/issues/303)。

## 方案 6：FFmpeg 音乐卡点与快切混剪

- **程序与入口：** FFmpeg 执行剪合；librosa 分析音乐节拍/起音；PySceneDetect 提取场景边界。拟建 `$video-cut-beat-montage`，复用 `$video-cut-ffmpeg`。这是自建工作流，不是已找到的现成同名 Skill。
- **制作流程：** 镜头切分 → 音乐节拍与能量分析 → 给镜头匹配时长与切点 → 应用运动/变速 → 转场和混音 → 渲染。场景检测给边界，广告语义和素材取舍仍由 Agent 负责。
- **关键帧与运镜：** 将节拍点转为推近、冲击缩放、短暂停顿、快慢切换和闪白等配方参数；实现时需区分视频速度和音频速度，检查转场重叠及最终时长。
- **需要补齐：** 节拍误检修正、镜头评分、预设编译、可变速曲线和视觉检查。基本节拍分析与场景检测不需要生成式视频模型；中文转写可按需加入 Whisper。
- **质量目标与交付：** 面向活动、运动、音乐驱动的广告，在限定风格内建立高质量模板。交付 MP4、节拍表和重建用 JSON；不默认产生桌面编辑器可复修工程，可另建方案 1 的工程适配。

依据：[librosa](https://github.com/librosa/librosa)、[ISC 许可证](https://github.com/librosa/librosa/blob/main/LICENSE.md)、[PySceneDetect 的 Python/CLI、Windows 发布与 BSD-3-Clause](https://github.com/Breakthrough/PySceneDetect)。

## 方案 7：Blender 三维产品广告

- **程序与入口：** Blender 原生 Python API 编排场景与渲染，FFmpeg 合成声音和交付。拟建 `$video-cut-blender-ad`；可以直接由 Agent 生成并调用 Python 脚本，初期不需要额外 MCP。
- **制作流程：** 产品模型与材质 → 灯光/摄影模板 → 镜头设计 → 相机和物体动画 → 分镜预览 → 图像序列 → 配音、字幕与成片。已有实拍素材可加入 Blender 的合成/视频序列流程，或回到方案 1。
- **关键帧与运镜：** 推拉、环绕、轨道运动、对焦、物体旋转和拆解动画属于场景中的真实三维控制，和二维画面缩放的参数不同。
- **需要补齐：** 产品模型与材质、摄影场景库、相机配方、渲染预算与脚本 Skill。没有合格三维资产时，不能靠一句提示词保证产品外观准确。
- **质量目标与交付：** 面向少量精致产品镜头，交付 `.blend`、脚本、图像序列与 MP4。它提供比通用二维编辑更大的三维表现空间，但制作成本取决于资产与画面要求，不宜替代所有日常混剪。

依据：[Blender 官方说明](https://www.blender.org/about/)、[官方许可及 Python API 说明](https://www.blender.org/about/license/)、[命令行参数文档](https://docs.blender.org/manual/en/latest/advanced/command_line/arguments.html)。

## 方案 8：Glaxnimate 二维品牌与花字包装

- **程序与入口：** Glaxnimate 制作矢量动画与可编辑模板，Python 脚本绑定品牌参数，图像序列/视频输出交给 FFmpeg 或方案 1 合成。拟建 `$video-cut-glaxnimate-ad`。
- **制作流程：** 品牌规范 → Logo/花字/标签模板 → 替换文本、颜色、路径和时长 → 渲染动画层 → 与商品素材合成。先建设一组可重复使用的模板，再扩大样式库。
- **关键帧与运镜：** 路径运动、补间、缩放旋转、遮罩揭示和矢量形变；商品素材本身的摄影运动交给剪辑主内核。
- **需要补齐：** 参数化模板、Agent 脚本入口、Windows 批处理与透明图像序列验收。官方已说明有脚本、逐帧图像渲染和无 GUI 图像渲染选项；具体 Windows 版本的批量导出路径仍需实测。
- **质量目标与交付：** 最适合统一品牌包装、Logo 片头和卖点花字，交付可编辑动画源文件、参数表、图像序列和 MP4。它是包装模块，不提供完整的素材理解与叙事剪辑流程。

依据：[KDE 官方功能、Windows 下载与 GPL-3.0+](https://apps.kde.org/glaxnimate/)、[Python 属性修改与逐帧渲染](https://glaxnimate.org/contributing/scripting/examples/)、[无 GUI 渲染功能公告](https://glaxnimate.org/news/releases/0.5.2/)。

## 方案 9：Manim 数据与技术解释广告

- **程序与入口：** Manim Community + FFmpeg；可以改造 `browser-use/video-use` 中现有的 `skills/manim-video/SKILL.md`。建议本地入口 `$video-cut-manim-ad`。
- **制作流程：** 产品卖点/数据 → 解释型分镜 → Manim Python 场景 → 文字、图形和图表动画 → 配音与字幕 → 成片。适合图形承担主要叙事的广告。
- **关键帧与运镜：** 使用程序化的对象变换、路径、移动相机和场景时序，封装图表聚焦、数字跳变、卖点高亮与步骤切换等配方。
- **需要补齐：** 把教学向 Skill 改为广告向工作流，核查旧参考版本与当前 Manim 兼容性，改写 Windows 前置准备和中文字体规范。普通文字方案可以不用 LaTeX；只有需要公式时才添加相应依赖。可选云端配音需改为本地开源配音或已有录音。
- **质量目标与交付：** 面向 SaaS、技术产品和数据比较广告，交付 Python 场景、资源、字幕与 MP4。它能精确制作动画，但不能替代一般实拍时间线编辑器。选用该仓库的 Manim 子 Skill，不照搬主工作流的云端服务默认配置。

依据：[Manim Community / MIT](https://github.com/ManimCommunity/manim)、[现有 manim-video Skill](https://github.com/browser-use/video-use/blob/43cfc566833548093455c9d4a46bd69913b7e552/skills/manim-video/SKILL.md)、[官方 Windows 安装与可选 LaTeX](https://docs.manim.community/en/stable/installation/uv.html)。

## 方案 10：综合 AI 广告生产系统

- **程序与入口：** 方案 1 的 Shotcut/MLT 作为最终时间线；方案 4 的开源改造 Recap 组织内容；ComfyUI + Apache-2.0 的 Wan2.1-VACE 提供生成/视频编辑；MODNet 做人像 alpha；按需加入方案 7、8 的包装模块。拟建总入口 `$video-cut-ai-ad-studio`，配套 `$video-cut-ai-local`、`$video-cut-motion-presets`、`$video-cut-native-qc`。
- **制作流程：** 广告简报 → 本地语音/画面分析 → 脚本与素材规划 → 确定性剪辑 → 按需生成特效/抠像/包装素材 → 命名运镜 → 中文字幕与声音 → 逐段检查 → 可编辑工程与最终成片。生成模型作为素材/特效模块，最终时间线仍由明确的工程和参数控制。
- **关键帧与运镜：** 共享镜头预设协议，编译到 Shotcut 或其他后端；模型输出的镜头也进入同一素材和时间线检查流程。复杂跟踪、特效一致性与关键帧衔接需要独立验收。
- **需要补齐：** 跨工具适配器、统一素材/时间轴、模型作业队列、资源调度、模板库和失败恢复。必须冻结节点、模型与许可证，不能因 ComfyUI 本体开源就认为任何第三方节点或权重都合格。
- **质量目标与交付：** 这是向完整剪映类制作能力靠近的长期架构，覆盖面最大，建设量也最大。交付 `.mlt`、中性制作计划、AI 工作流与模型记录、字幕、素材和 MP4；并非现成的一键整包。
- **分辨率与资源边界：** Wan2.1-VACE-1.3B 官方示例约为 480×832，14B 约为 720×1280。1.3B 的输出放大并编码为 1080p，不等于生成了原生 1080p 细节。不同模型的显存、耗时与本机兼容性未测，不承诺实时生成；不选用带 RAIL-M 的 VACE-LTX 版本。

依据：[ComfyUI 开源代码与 Windows 原生运行](https://github.com/Comfy-Org/ComfyUI)、[VACE 各模型的许可证与尺寸](https://github.com/ali-vilab/VACE)、[ComfyUI 官方 VACE 工作流](https://docs.comfy.org/tutorials/video/wan/vace)、[MODNet 代码与模型许可](https://github.com/ZHKKKe/MODNet#license)。

## 所有方案共用的设计

**广告创意。** 可复用已安装的 `$video-cut-ad-creative` 做受众、卖点、Hook、证据、CTA 和文案变体；这负责广告策划，不代替剪辑内核。自动生成的脚本仍需要核对商品事实与成片效果。

**素材与时间轴。** 素材记录保留来源、文件哈希、画幅、时长、帧率和用途；剪辑计划记录源素材区间及成片位置。中性制作计划和各编辑器原生工程是不同交付物，通过有版本的适配器转换，不能直接混用。

**快速关键帧与运镜预设。** 拟建 `$video-cut-motion-presets`，初期封装推近、拉远、横移、Ken Burns、节拍缩放、淡入淡出；速度渐变单独标明后端是否支持。预设包含片内帧坐标、中心/缩放参数、插值、画幅裁切与最小安全缩放。Recap 的秒时间轴在转换时按工程帧率换算；二维画面移动与 Blender 三维相机保持各自参数类型。主体自动跟踪不计入这些基础预设的现成能力。

**开源 AI 默认候选。** Whisper 的代码和模型权重为 MIT；Kokoro 推理库和 Kokoro-82M 权重为 Apache-2.0，支持普通话；本设计的 VLM 明确选择 Apache-2.0 的 Qwen2.5-VL-7B-Instruct，不将整个 Qwen 系列的所有版本视为同一许可证。提供服务的 Python 入口、时间戳和音频契约需要开发验证；这些模块没有在本轮自动安装。[Whisper](https://github.com/openai/whisper)、[Kokoro 推理库](https://github.com/hexgrad/kokoro)、[Kokoro-82M 模型](https://huggingface.co/hexgrad/Kokoro-82M)、[指定 Qwen VLM 模型](https://huggingface.co/Qwen/Qwen2.5-VL-7B-Instruct)。

**交付与检查。** 拟建 `$video-cut-native-qc`，检查成片尺寸、帧率、时长、音画同步、字幕完整性、字体、裁切黑边、异常黑帧、声音峰值和素材路径。能交付原生工程的路线还要验证工程重开、修改一处字幕/镜头后再次导出。FFmpeg 路线交付重建脚本和 JSON，未经转换不宣称可在桌面编辑器中复修。

## 用什么证明达到目标

以下是拟定验收项目，不是已经通过的测试。先按方案适用范围制作样片；只有样片通过，才宣称该路线在相应类型的广告上达标。

## 开源边界和推荐实施顺序

许可证筛选采用明确许可的程序、推理代码和指定权重。Shotcut/Kdenlive/Glaxnimate 为 GPL 系列；Shotcut MCP 与 DCC 适配器为 MIT；AMMIROSOH 适配器为 Apache-2.0；Recap 和 Manim 为 MIT；Concat 为 AGPL-3.0 系列；librosa 为 ISC；PySceneDetect 为 BSD-3-Clause；Blender 二进制整体许可为 GPL-3.0-or-later；ComfyUI 为 GPL-3.0；本文指定的 VACE、MODNet、Kokoro 与 Qwen VLM 候选有 Apache-2.0 代码或权重依据。FFmpeg 的具体许可取决于构建选项，使用仅含开源组件的构建，并保留版本与许可记录。[FFmpeg 官方许可说明](https://ffmpeg.org/legal.html)

本设计不采用剪映相关客户端/SDK、Remotion 内核、付费云端 AI 默认依赖。HyperFrames/Lumen 的默认 GSAP 依赖此前未满足严格纯开源筛选，因此也不作为这 10 套的默认生产路径；替换动画依赖并经过渲染验证后可另行评估。[Remotion 官方许可解释](https://www.remotion.dev/docs/license/faq#is-remotion-open-source)、[GSAP 许可](https://gsap.com/community/standard-license/)

建议顺序：

1. **先方案 1：** 打通原生 Windows 的可编辑工程、运镜和真实 MP4，用电商样片验证主线。
2. **接方案 4：** 在已有剪合能力上加入开源转写、解说、配音和叙事；保留现成 Recap 契约并补转换器。
3. **按广告类型选扩展：** 批量投放加方案 3，卡点加方案 6，品牌包装加方案 8，三维镜头加方案 7，技术解释加方案 9。
4. **最后形成方案 10：** 在已验收的确定性制作流程上加入生成特效、抠像和统一调度。方案 2 是 Kdenlive 复修路线备选；方案 5 独立做研发验证。

这一路径优先保证可交付的广告成片和可修改工程，再扩展 AI、模板与规模化能力。
